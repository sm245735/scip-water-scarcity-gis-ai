## 🎯 核心原則

### 「安全、穩定永遠優先於速度」

> 寫死一句話，忘記其他細節時回到這句：
> **「能慢一點、但不能壞。」**

當速度與安全衝突時，永遠選安全。具體的優先順序：

1. **資料完整性**（不能掉資料、不能寫壞檔案）
2. **可恢復性**（任何步驟失敗都能從 checkpoint 接續，不從頭來）
3. **可觀察性**（跑什麼、跑到哪、卡哪都看得到）
4. **速度**（能快就快，但只在不犧牲上面三點時）

---

## ✅ 必須做（Do）

### 1. 長任務一定要有 checkpoint

任何預期超過 **10 分鐘** 的批次任務：

- 每完成一個 batch / 單位就寫一次 checkpoint 到磁碟
- checkpoint 路徑命名清楚：`xxx_partial.json` / `xxx_shardN.json`
- 啟動時先讀 checkpoint 跳過已完成的項目（**resumable 設計**）
- 失敗時不要從頭重來，從最後一次成功的 checkpoint 接續

**範例**（ICML 2026 翻譯 6636 篇）：
- 原本無 checkpoint → 一次跑 14.5 小時 + 1850 篇失敗 = 全部要重來
- 後來有 checkpoint → 中斷後重啟 5 秒內接續

### 2. 操作前先驗證規模與狀態

動手前先確認：
- 資料總量、已處理多少、剩餘多少
- 失敗的散佈（整段失敗？散落？前面 or 後面？）
- 預估時間、剩餘 token / quota

**不要**對未知規模直接 `for x in ALL: do_thing(x)`，先 sample / 統計再決定策略。

### 3. 失敗要分類，不要無腦重試

把失敗分成至少兩類：
- **可重試**（timeout、網路抖動、5xx）：sleep + retry 3 次
- **不可重試**（bad input、JSON parse fail、4xx）：記錄到 `failed_ids` 留到最後統一處理

不要無限 retry，不要把整個 batch 跳過當作「處理完」。

### 4. 平行處理要分階段驗證

加 worker 數 / 換更大 batch / 改 model 之前：
1. **先小規模 pilot**（3-10 個 process 同跑、看有沒有 rate limit）
2. 確認 OK 再上完整規模
3. 上完後盯前 1-2 個 batch 的 log 確認沒掉資料

**反面教材**：直接從 1 worker 跳到 16 worker，結果某個 step race condition 把 200 篇翻譯寫進同一個 key。

### 5. 重要操作要可中斷、可回滾

- 寫檔前先確認有 backup 或可重現
- 不要做「不可逆的批次操作」前不先備份（rm 萬個檔案、git push --force 大量 commit、DB DROP TABLE）
- 大量寫入前先在 1 個 sample 上 dry-run

### 6. 進度可被觀察

跑的時候要能在 log 看到：
- `[start] N 總數`
- `[batch X/Y] OK | 已完成 / 總數 | 經過時間 | ETA`
- `[summary] 成功 / 失敗 / 跳過`

不要悶著跑好幾小時，沒人知道跑到哪。Cron job 用 stdout 印進度，notify_on_complete 一定要設。

## ❌ 禁止做（Don't）

### 1. 不要「先跑再說」

- 沒寫 checkpoint 就跑長任務 → 中斷就全毀
- 沒看失敗模式就 retry 100 次 → 浪費 quota + 還是會失敗
- 沒算過 quota 就送 → 跑到一半 429

### 2. 不要用「刪除」當作解法

- 失敗的 row 不要直接 delete，留到 log 或 `failed_ids` 裡
- 舊版本檔案不要 rm，git history 已經有了
- 「我重來一份新的就好」 → 通常會發現舊的有重要東西

### 3. 不要無腦把 worker 數往上加

- 1 個 API key 通常撐不住 10+ 個並行（會 rate limit）
- 加 worker 前先 pilot、再評估
- 預設保守值：**4 worker** 就好，速度真的不夠再往上調

### 4. 不要拿不確定的東西冒險

- 不熟的套件、不熟的 API → 先 sample 跑 1 個，不要直接 batch 1000
- 別人寫的腳本、copy-paste 的 code → 不要沒看就執行
- token / key / 密碼 → 絕對不貼進 chat、log、commit 訊息

### 5. 不要「為了快而犧牲可恢復性」

壞掉 30 分鐘能重來 ✓
壞掉 3 小時的東西要重來 ✗
壞掉 12 小時的東西要重來 ✗✗

**重新做 N 次的成本 > 慢 N% 預防的成本**，永遠是後者划算。

## 🔁 操作前的決策檢查清單

開始任何 > 10 分鐘的任務前，過這份清單：

- [ ] **預期多久？** < 10 分鐘：直接做；> 10 分鐘：要有 checkpoint
- [ ] **有沒有 resumable？** 中斷後能不能從 checkpoint 接續？
- [ ] **失敗會怎樣？** 最壞情況是什麼？可不可以 rollback？
- [ ] **要 pilot 嗎？** 第一次跑這個規模/工具/model：先 sample 1-10 個
- [ ] **進度有顯示嗎？** 跑的人（你 or agent）看 log 知道跑到哪
- [ ] **失敗有分類嗎？** timeout vs bad input 分開處理
- [ ] **寫入是 atomic 嗎？** 寫到一半 crash 不會留半成品
- [ ] **有通知嗎？** 完成的時候要主動 notify，不要悶著

## 📚 案例對照

### ✅ 好的實作（2026-06 ICML 2026 補跑翻譯）

```python
# /tmp/icml_topup_parallel.py
# - 讀既有 checkpoint（4288 篇）→ 只跑剩 2348 篇
# - 4 worker × batch=25 → 平行但保守
# - 每個 worker 寫自己的 shard checkpoint + append 到 global
# - 每 batch 印進度 + ETA
# - 失敗分類：mmx 失敗 retry 3 次，整 batch 跳過留 failed_ids
# - 完成後 merge 寫回 Excel
```

**效果**：預估 ~1 小時完成，進度可觀察，失敗不擴散。

### ❌ 壞的實作（2026-06 ICML 2026 初跑）

```python
# /tmp/icml_translate_all.py  初版
# - 沒分失敗類型，整 batch fail 就 skip
# - 14.5 小時跑下來 1850 篇 missing、Status 都還寫 OK
# - 失敗散落在整個檔案 → 重跑 2348 篇才知道哪些沒過
# - 中斷就全毀（checkpoint 寫太晚、寫失敗也視為完成）
```

**教訓**：缺上面清單裡的「失敗分類」、「進度散落觀察」、「atomic write」。

## 📌 最後一條原則

> **「如果一個操作不能被 undo，就必須有 backup。」**
> **「如果一個操作跑了 N 小時，必須能在 < 1 分鐘內接續。」**
> **「如果一個操作可能失敗，必須事前想好 fallback。」**

違反這三條，停下來重新設計流程。
