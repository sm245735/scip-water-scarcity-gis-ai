---

## 第 1 頁｜封面

> *「水資源缺水風險評估，以新竹寶山第二水庫為例。這個研究從半導體供應鏈視角，用 LSTM 時間序列預測，評估竹科缺水風險。」*

**🔑 口試重點：為何是半導體視角？**
- 新竹科學園區年產值 4 兆元，每日用水 20 萬噸
- 寶山第二水庫是竹科主要水源，水庫一出問題，半導體供應鏈跟著緊張
- 研究問題：極端氣候下，竹科供水會不會缺水？能不能提前預警？

---

## 第 2 頁｜研究背景與動機

### 1. 竹科：台灣半導體心臟
> *「新竹科學園區年產值超過 4 兆元，每日用水量約 20 萬噸，對水庫依賴程度極高。」*

**📌 資料怎麼來的：** 4 兆元數字來自國科會新竹科學園區管理局年報；20 萬噸/日是水利署統計新竹地區農業與工業用水量估算。這些是已知文獻數字，不是模型算出來的。

### 2. 水庫：單一風險來源
> *「寶山第二水庫為竹科主要供水來源，蓄水量直接影響園區運營與產能。」*

**📌 資料怎麼來的：** 寶山第二水庫（ID=10405）在水利署水庫統計系統中，屬於新竹地區供水調度核心。這從水利署公開的供水管線與水源配置文件可以確認。

### 3. 極端氣候：威脅加劇
> *「2021 年百年大旱、2023 年豐水期缺水，傳統線性模型難以捕捉突發性水文變化。」*

**📌 資料怎麼來的：** 2021 年大旱是實際事件，翡翠水庫、石門水庫都創下歷史低水位；這說明線性迴歸或季節性分解（ARIMA）無法處理降雨-蓄水量之間的非線性延遲關係（可能落後 7~30 天）。

### 4. LSTM 優勢
> *「LSTM 可學習降雨-蓄水量非線性動態關係，30 天前預警爭取應變黃金時間。」*

**📌 為何選 LSTM：**
- 傳統水文模型（SWAT）需要很多手動設定參數（蒸發係數、土壤滲透等）
- LSTM 是端對端資料驅動，只需要輸入過去 30 天的降雨與蓄水量，模型自己學非線性關係
- 30 天滑動窗口是本研究設定的預警緩衝期（可依需求調整）

## 第 3 頁｜研究架構

> *「整體研究流程分四個階段：資料來源 → 資料處理 → 模型訓練 → 風險評估。」*

**🔑 流程說明（逐行）：**

```
TCCIP 降雨 ＋ 水庫水情   →   rainfall→storage 映射   →   LSTM 回歸 ＋ BiLSTM 分類   →   缺水預警
```

- **TCCIP 降雨**：台灣氣候變遷推估資料（水利署與學術界合作的高解析度網格降雨資料，空間解析度 1×1 km）
- **水庫水情**：水利署每日統計表，已匯入 PostGIS 資料庫（409,248 行，112 座水庫）
- **rainfall→storage 映射**：指「降雨–蓄水直接映射」，因為寶二 inflow/outflow 缺值 97.8%，所以繞過流率，直接用降雨預測蓄水量
- **LSTM 回歸**：預測明日蓄水量（連續值）
- **BiLSTM 分類**：預測 30 天內是否觸發缺水（二元分類）
- **缺水預警**：輸出風險等級，串接到 ArcGIS 前端地圖

### 左區：水庫歷史水情資料

| 項目 | 內容 |

| **來源** | 水利署水庫統計表（每日更新） |
| **時間範圍** | 2016-01-01 ~ 2026-01-01（完整 10 年）|
| **水庫數量** | 112 座（含寶二 id=23） |

| **儲存位置** | `reservoir_daily` schema |

**📌 資料怎麼來的：** 水利署每日 17:00 更新前一日水庫水情，包含：水庫名稱、日期、有效蓄水量、進水量（inflow）、出水量（outflow）、蓄水率等。匯入方式：`水庫Statistics_每日收集_host.py`（Docker cron job）。

**📌 資料處理做了什麼：**

2. **is_imputed 旗標**：補值前先標記，內插 ≤7 天的補值標為 1，超過保留 NaN，確保研究可重現性
3. **寶二篩選**：只取 `reservoir_id = 23`（寶山第二水庫）

### 右區：TCCIP 頭前溪降雨資料

| 項目 | 內容 |
|------|------|
| **來源** | TCCIP 高解析度網格降雨 |
| **時間範圍** | 2016-01-01 ~ 2023-12-31（8年）|
| **格點數量** | 43 個格點覆蓋頭前溪集水區 |
| **空間解析** | 約 1×1 km |

**📌 資料怎麼來的：** TCCIP（Taiwan Climate Change Projection and Information Platform）由國家災害防救科技中心與水利署合作，透過都卜勒雷達、雨量站融合技術，產出網格式降雨資料，比單一雨量站更能反映集水區整體降雨。

**📌 資料處理做了什麼：**
1. **空間加權平均**：頭前溪集水區覆蓋 43 個 TCCIP 網格，每格依面積加權平均，計算「集水區平均降雨量」
2. **地理空間查詢**：使用 PostGIS `ST_Contains` 對集水區邊界（geom）與 TCCIP 網格（另一張表）做空間聯集，避免幾何碎片造成 False Negative（重要修復記錄在 Commit `5022c3b`）
3. **與水庫日期對齊**：降雨日表（逐日）與水庫水情日表（逐日）以日期 key 做 join

**⚠️ 重要發現（口試亮點）：**
> 本研究一開始想用進水量（inflow）和出水量（outflow）來建模，符合傳統水平衡概念。但分析發現，寶山第二水庫 2016-2023 年間，inflow 與 outflow 各自只有 25 天有觀測值，觀測率 0.9%。原因是寶二屬於「離槽水庫」，流率不是每日例行記錄。因此本研究改用「降雨→蓄水量直接映射」，繞過不可靠的中介變數。這是資料限制下的務實取捨，也是研究亮點之一。

## 第 5 頁｜LSTM 回歸模型架構

```
Input: (30, 7)
  → LSTM(64, tanh, return_sequences)
  → Dropout(0.2)
  → LSTM(32, tanh)
  → Dropout(0.2)
  → Dense(16, ReLU)
  → Dense(1)  → 明日蓄水量
```

**🔑 逐層解釋：**

| 層 | 設定 | 意義 |
|----|------|------|
| **Input (30, 7)** | 30 天 × 7 個特徵 | 用過去 30 天預測明天 |
| **LSTM(64)** | return_sequences=True | 第一層要往下傳遞序列給第二層 |
| **Dropout(0.2)** | 隨機斷開 20% 神經元 | 防止過擬合 |
| **LSTM(32)** | return_sequences=False | 只取最後一個時間步輸出 |
| **Dense(16)** | ReLU 激活 | 全連接層，提取高階特徵 |
| **Dense(1)** | 線性輸出 | 明日蓄水量（萬噸）|

**📌 輸入的 7 個特徵（資料怎麼來的）：**

| 特徵名 | 意義 | 資料來源 |
|--------|------|----------|
| `basin_rainfall_tccip_mm` | 當日集水區平均降雨（mm）| TCCIP 網格加權平均 |
| `rainfall_7d_sum` | 過去 7 天累積降雨（mm）| 由上列衍生 |
| `rainfall_30d_sum` | 過去 30 天累積降雨（mm）| 由上列衍生 |
| `effective_storage` | 當前有效蓄水量（萬噸）| 水利署水庫統計表 |
| `storage_diff_1d` | 前日蓄水量變化（萬噸）| 由上列差分計算 |
| `doy_sin` / `doy_cos` | 年週期編碼（三角函數）| 日期 day-of-year 編碼 |

**📌 訓練/測試集切分：**
- **訓練集**：2016-01-01 ~ 2021-12-31（6 年，約 2,284 天）
- **測試集**：2022-01-01 ~ 2023-12-31（2 年，638 天）
- 為何這樣切：時間序列嚴禁random split，必須保留時間順序；2022 年開始是旱情退去後的復胖期，用未見過的資料測試模型泛化能力

**📌 正規化方式：** MinMaxScaler 只 fit 訓練集，transform 測試集，避免未來資訊洩漏（data leakage）

## 第 6 頁｜缺水風險分類器

```
缺水定義：effective_storage < 1,200 萬噸  →  缺水標籤 = 1

Input: 30 天滑動窗口
  → BiLSTM(64, return_sequences)
  → Dropout(0.3)
  → BiLSTM(32)
  → Dropout(0.3)
  → Dense(16, ReLU)
  → Dense(1, sigmoid)  → 機率（30天內缺水=1）
```

**🔑 與回歸模型的不同：**

| 差異 | LSTM 回歸 | BiLSTM 分類 |
|------|---------|-------------|
| 任務 | 預測明日蓄水量（連續值）| 預測 30 天內是否缺水（二元）|
| 輸出 | 1 個數值（萬噸）| 機率（0~1）|
| 雙向 | 否 | 是（BiLSTM 可以看前後 context）|
| 類別不平衡 | 無 | 有（缺水事件只佔 4.7%）|

**📌 標籤怎麼定義的：**

```python
# 向前看 30 天內是否曾低於 1,200 萬噸
for i in range(len(df) - 30):
    future_window = storage[i+1 : i+1+30]
    if (future_window < 1200).any():
        labels[i] = 1   # 缺水
    else:
        labels[i] = 0   # 正常
```

**📌 類別不平衡怎麼處理的：**
- 缺水標籤=1 的樣本只佔整體 4.7%（高度不平衡）
- 使用 `class_weight` 調整：讓模型對少數類（缺水）給予更高懲罰代價
- 公式：`class_weight = {0: 1, 1: samples_0 / samples_1}` ≈ 20倍

**📌 為何選擇 1,200 萬噸作為閾值：**
- 寶山第二水庫總容量約 3,100 萬噸
- 1,200 萬噸 ≈ 38.7% 蓄水率
- 這個數字低於水利署「一階限水」觸發線（多數水庫在 20~40% 蓄水率進入限水）
- ⚠️ 口試時老師可能會挑戰這個數字，建議補充文獻依據

- MAE 211.8 萬噸 ≈ 6.8% 的相對誤差，對水庫管理者而言，誤差在可接受範圍內（不會用單一數字做決策，通常看趨勢）
- Max Error 528.8 萬噸發生在 2023 年初（豐水期來臨、水位快速回升時），模型來不及跟上突變，這是 LSTM 的已知弱點（對快速相位轉換反應慢）

## 第 8 頁｜模型表現 — 缺水風險分類器

> **測試集：638 天（2022-01-01 ~ 2023-12-31）**

| 指標 | 數值 | 解釋方式 |
|------|------|----------|
| **AUC-ROC** | **0.981** | 模型區分「缺水 vs 正常」的能力，0.981 接近 1.0，代表區分能力極強 |
| **Recall** | **100%** | 所有缺水事件，模型全部命中，零漏報 |
| **Accuracy** | 77.6% | 整體正確率（但受類別不平衡影響）|
| **Precision** | 17.3% | 報了 100 次缺水警示，有 83 次是誤報 |
| **F1** | 0.296 | Precision 和 Recall 的調和平均（因為 Precision 太低所以 F1 也不高）|

**📌 圖怎麼來的：**

ROC 曲線（`classifier_roc.png`）：
- X軸：False Positive Rate（誤報率）
- Y軸：True Positive Rate（命中率）
- 曲線越靠近左上角越好；AUC = 0.981 表示分類邊界非常清晰

Confusion Matrix（`classifier_cm.png`）：
- 行：實際；列：預測
- 左上 TN / 右上 FP / 左下 FN / 右下 TP
- 用途：一眼看出 FN（漏報）和 FP（誤報）數量

**📌 結果怎麼解讀（口試最重要的部分）：**

**Q：AUC = 0.981 是什麼意思？**
> 代表模型有 98.1% 的機率能區分「明天會缺水」和「明天不會缺水」這兩個案例。這是非常高的區分能力，隨機猜測只有 50%。

**Q：為何 Recall = 100% 最重要？**
> 因為在水資源風險管理裡，**漏報（FN）的代價遠比誤報（FP）高**。
> - 漏報：真的缺水了但沒發現 → 來不及应变 → 停水、產業損失
> - 誤報：沒缺水但發了警示 → 評估後沒事 → 虛驚一場
> 所以模型策略是：「寧可誤報，不可漏報」。

**Q：Precision = 17.3% 很低，會有問題嗎？**
> 在這個應用情境下可以接受，因為：
> 1. 缺水事件只佔 4.7%（極度類別不平衡）
> 2. 30 天窗口很長，任何一天低於 1,200 萬噸就觸發
> 3. 誤報代價低：收到警示 → 研判 → 決定是否行動，不會直接停水
> 4. 可以透過調整 threshold 犧牲 Recall 換 Precision，但本研究選擇保守策略（Recall 優先）

**Q：要怎麼改善 Precision？**
> 調整分類閾值（threshold）：
> - threshold↓ → 更容易判定為缺水 → Recall↑, Precision↓
> - threshold↑ → 只有很確定才判定缺水 → Precision↑, Recall↓
> 目前 default = 0.5，若口試老師問，可以說「這是留給決策者的調整空間」

## 第 9 頁｜結果解讀（口試重點）

> **這頁是精煉的嘴巴說法，建議全部背起來**

### 為何 Recall = 100% 很重要？
> *「模型從未漏掉任何一次缺水事件。對於水資源風險管理，漏報比誤報代價高得多。本研究的核心原則是：寧可謹慎，不可遺漏。即使 Precision 偏低，只要 Recall 高，就能確保每次旱象都被提前發現。」*

### 如何解釋 Precision = 17.3%？
> *「缺水事件在測試集只佔 4.7%，屬於高度類別不平衡。同時，30 天的預測窗口很長，只要未來 30 天內有任何一天低於閾值，就會觸發警示。誤報的代價很低——收到警示後，相關單位可以評估、決定是否行動。最終，這是一個可以透過調整 threshold 來取捨的參數，本研究目前優先確保不漏報。」*

## 第 13 頁｜請教授指導

> *「感謝聆聽，敬請指導。以下是我的研究問題，請老師提供建議。」*

### 口試預測問題清單（先準備好）

**Q1：模型是否還需要加入其他特徵？**
> 預期回答：可以考慮（1）蒸發量、氣溫（影響散發）、（2）颱風指標（二元變數）、（3）上游水庫放水量。現階段受限於資料可用性，蒸發量在高解析度網格尺度較少，TCCIP 主要提供降雨。未來若取得水利署蒸發皿資料可進一步整合。

**Q2：對照組的選擇是否足夠？**
> 預期回答：目前規劃 SVR（支持向量回歸）、ARIMA（傳統時間序列）、Random Forest（集成學習），這三個剛好代表：傳統統計、淺層機器學習。未來可加 XGBoost 或 Transformer-based 時間序列模型。

**Q3：缺水閾值 1,200 萬噸的設定是否合理？**
> 預期回答：這個數字約佔總容量 3,100 萬噸的 38.7%，符合水利署「一階限水」參考線（20~40%）。但建議老師提供文獻或實務上的標準，若有更精確的竹科用水量與寶二供水比例，也可以用倒推方式設定閾值。

**Q4：實驗結果的呈現方式是否有建議？**
> 預期回答：目前用 MAE/AUC/Recall，歡迎老師提供其他評估框架，特別是針對時間序列預測的不確定性量化（如置信區間、預測區間）。
